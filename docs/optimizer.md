# Оптимизатор состава: MILP поверх xPts

Шаг 6. `src/fplcopilot/core/{strategy,candidates,optimizer,plan}.py` — детерминированный слой
решений: **LLM здесь не считают ничего**. Вход — xPts v0 по турам горизонта (`core/xpts`),
состав менеджера, банк, оценка бесплатных трансферов; выход — лучшие 11, top-3 маршрутов одного
трансфера, многотуровый план с альтернативой Wildcard и запланированными фишками (Bench Boost /
Triple Captain в заданном туре) и структурированные причины (`out_problem`, `Δ xPts`,
`risk_note`). Агент поверх этого только объясняет.

```
predict_all(gw) для gw ∈ горизонт ─▶ Candidate{xpts_by_gw, variance_by_gw, price, ownership}
Squad (picks последнего тура, bank, FT) ─▶ build_pool (состав + top-120 + дешёвые энейблеры)
diagnose_squad ─▶ SquadIssue[]                        ─▶ rationale ходов, правило WC
build_model (одна MILP на всё) ─▶ HiGHS ─▶ best_xi | single_transfer | plan_transfers
plan_snapshots (006_plans.sql) ◀─ save_plan / latest_plan / diff_plans
```

```bash
uv run python -m fplcopilot.core.optimizer --manager 895045 --gw 5 --strategy balanced --xi
uv run python -m fplcopilot.core.optimizer --manager 895045 --gw 5 --transfer [--allow-hit] [--horizon 3]
uv run python -m fplcopilot.core.optimizer --manager 895045 --gw 5 --plan --horizon 5 [--save] [--wc|--no-wc]
uv run python -m fplcopilot.core.optimizer --manager 6856911 --plan --chip 8:bboost [--chip 7:3xc]
uv run python -m fplcopilot.core.optimizer --manager 895045 --gw 5 --diagnose
# общие флаги: --exclude 1,2 (не покупать) --keep 3 (не продавать) --pool 120 --time-limit 90 --json
```

## Солвер

PuLP 3.3 + **HiGHS** через `highspy` 1.15 (Python 3.12, macOS arm64 — ставится колесом, без
компиляции). CBC из комплекта PuLP на этой машине не запускается (`Bad CPU type in executable`
— бинарь x86_64 без Rosetta), поэтому `OPTIMIZER_SOLVER=auto` выбирает HiGHS, а CBC остаётся
запасным вариантом для Linux/CI. Настройки (`config.py` / `.env`): `OPTIMIZER_TIME_LIMIT_S=90`
на один solve, `OPTIMIZER_MIP_GAP=0.001`, `OPTIMIZER_POOL_SIZE=120`. При срабатывании лимита
времени план помечается `time_limit_hit` и печатается «(time limit hit)».

## Формулировка (`optimizer.build_model`)

Одна модель обслуживает все три режима. Множества: игроки пула `P` (позиция, клуб, цена),
туры горизонта `W = {g0, …, g0+H−1}`, слоты скамейки `{13, 14, 15}` (полевые; слот 12 —
запасной вратарь).

**Переменные.** Бинарные `squad[p,w]`, `start[p,w]`, `cap[p,w]`, `bench[p,s,w]` (полевые),
`t_in[p,w]`, `t_out[p,w]`; непрерывные `paid[w] ≥ 0`, `itb[w] ≥ 0`; целые `ft[w] ∈ [1, 5]`
(`ft[g0]` — константа из оценки FT). Вице-капитан не моделируется — берётся лучший стартер
после капитана при извлечении решения.

**Ограничения (на каждый тур w).**

| группа | условие |
|---|---|
| состав | `Σ squad = 15`; по позициям ровно 2/5/5/3; `Σ_{клуб} squad ≤ 3` |
| стартовые 11 | `start ≤ squad`; `Σ start = 11`; GKP = 1, DEF 3–5, MID 2–5, FWD 1–3 |
| капитан | `cap ≤ start`; `Σ cap = 1` |
| скамейка | полевые: `Σ_s bench[p,s,w] = squad − start`, `Σ_p bench[p,s,w] = 1` для каждого слота; вратарь: `squad − start` линейно идёт в слот 12 |
| непрерывность | `squad[p,w] = squad[p,w−1] + t_in − t_out` (для g0 — текущий состав); `t_in + t_out ≤ 1` |
| трансферы | `Σ t_in = Σ t_out ≤ max_transfers[w]` (режимы ниже); `keep` → нет `t_out`, `exclude` → нет `t_in` |
| бюджет | `itb[w] = itb[w−1] + Σ price·t_out − Σ price·t_in`, `itb ≥ 0`; `itb[g0−1] = bank` |
| хиты и FT | `paid[w] ≥ Σ t_in − ft[w]`; `ft[w+1] ≤ ft[w] − Σ t_in + paid[w] + 1`; `ft ≤ 5` |
| Wildcard в w | `paid[w] = 0`, лимит трансферов снят, `ft[w+1] ≤ ft[w] + 1` (FT сохраняются, правила 2026/27) |
| фишка в w | новых ограничений нет — Bench Boost / Triple Captain меняют только цель тура w (ниже); Wildcard и фишка в одном туре — ошибка `ChipPlanError` |

Динамика FT записана неравенством «≤» без вспомогательного бинарного `min`: FT входит в цель
только «в плюс» (ценность FT и меньше `paid`), поэтому оптимум неравенства совпадает с
`min(5, ft − used + paid + 1)`. Для отчёта траектория FT и хитов **пересчитывается детерминированно**
из трансферов (`extract_solution`), так что напечатанные FT/хиты — правильные даже там, где
солверу было безразлично. open-fpl-solver делает то же через бинарные состояния `ft_state ∈ 0..5`.

**Цель** (максимизация), `d_w = decay^(w − g0)`:

```
Σ_w d_w · [ Σ_p xpts[p,w]·(start + cap)                     # 11 + удвоение капитана
          + Σ_p Σ_s bench_w[s]·xpts[p,w]·bench[p,s,w]        # скамейка по слотам 13–15
          + Σ_{GK} bench_w[12]·xpts·(squad − start)          # запасной вратарь
          − λ · Σ_p variance[p,w]·start                      # риск-аверсия стратегии
          + ω · Σ_p ownership[p]·squad                        # шаблон (+) / дифференциалы (−)
          − 4 · paid[w]                                       # хиты
          + itb_value · itb[w]                                # £ в банке (за тур)
          + ft_value · (ft[w+1] − ft[w]) ]                    # FT начисляется, когда появляется
```

Последние два слагаемых — ровно как в open-fpl-solver (`dev/solver.py`, objective «regular»):
цены в миллионах, `itb_value · in_the_bank[w]` и `gw_ft_gain[w]` внутри дисконтированной суммы.
Первая версия с `itb_value` «за 0.1 млн в конце горизонта» продавала премиумов в последнем туре
ради банка — исправлено сверкой с источником.

### Фишки в туре (`ModelSpec.chips`, `plan_transfers(chips=…)`)

Пользователь фиксирует «фишка → тур» (`{8: "bboost"}`, `{7: "3xc"}`); тур фишки не выбирается
солвером — это условие, как `keep`/`exclude`. Меняется только слагаемое тура `w`:

```
Bench Boost в w:  Σ_p xpts[p,w]·(squad + cap)         # очки всех 15 + удвоение капитана
                  − λ · Σ_p variance[p,w]·squad        # риск всех 15: скамейка тоже играет
                  (бенч-слагаемые с bench_w[12..15] убраны — их роль «доля от автозамен» заменена
                   полным счётом, иначе скамейка считалась бы дважды)
Triple Captain в w: Σ_p xpts[p,w]·(start + 2·cap)     # капитан ×3; скамейка и риск — как обычно
```

Остальное (ownership, хиты, `itb`, `ft`, дисконт) не меняется. Поскольку модель многотуровая, BB
в туре w реально меняет решения до него: запасной, который без фишки весит 0.21 / 0.06 / 0.002 /
0.03, в туре BB стоит 1.0, и солвер копит FT и покупает скамейку под матчи этого тура
(тест `test_bench_boost_counts_all_15_and_changes_bench_transfers`, живой пример ниже). TC делает
выгодным апгрейд капитана, который без фишки не окупает FT
(`test_triple_captain_makes_a_captaincy_upgrade_worth_the_free_transfer`). Без фишек
коэффициенты цели прежние (`cap_extra = 1`, `scoring = start`) — JSON плана менеджеров 895045 и
6856911 совпал с прогоном до изменения (кроме новых пустых `chips_by_gw` / `notes`).

**Отчёт.** `LineupResult.chip` и `chip_points` — вклад фишки: при BB — Σ xPts скамейки тура,
при TC — ещё раз xPts капитана; `expected_points` тура уже включает этот вклад, а значит и
`expected_total`. При BB очки 15 не зависят от того, кто из них в старте, и солвер ставит 11
произвольно; для отчёта старт тура с BB восстанавливается `best_starters` (минимумы формации
лучшими по позиции + лучшие оставшиеся в пределах максимумов — жадность точна, это матроид
разбиения; сверено с MILP `best_xi` на случайных составах), цель от этого не меняется.
**Baseline** («без трансферов») строится с теми же фишками, поэтому «выигрыш к без трансферов» —
ценность трансферов при этих фишках, а не вклад самой фишки.

**Правила и валидация** (`validate_chip_plan`, правила 2026/27 — `fpl_rules_2026_27.md`,
`rules_digest.md`; нарушение — `ChipPlanError` с понятным текстом, не молчаливый пропуск):

| правило | проверка |
|---|---|
| моделируются только BB и TC | `freehit` — ошибка «Free Hit не моделируется»; `wildcard` — ошибка: WC сравнивается автоматически в первом туре горизонта |
| тур в горизонте | `gw ∈ [from_gw, from_gw + horizon − 1]` |
| одна фишка за тур | два условия на один тур — ошибка (вход инструмента — список `{gw, chip}`, дубли возможны) |
| фишка есть у менеджера | `chips_by_gw[gw]` из `load_inputs`: окно чипа в `bootstrap.chips` минус сыгранные (`chips_used` из истории), отдельно для каждого тура горизонта |
| по фишке на половину сезона | каждый чип дважды: GW1–19 и GW20–38 (первый набор сгорает после GW19) — одна и та же фишка дважды в одной половине — ошибка, в разных — можно |
| Wildcard + фишка в одном туре | `ModelSpec` с `wildcard_gw ∈ chips` — ошибка; в плане фишка в `from_gw` **отключает** WC-альтернативу (заметка в `notes`, метрика UI «не сравнивался»); `build_gameweek_plan(use_wildcard=true)` + фишка в первом туре — ошибка. Фишка в более позднем туре входит и в план, и в WC-альтернативу |

`chips_available` в контексте тура теперь — все доступные на `from_gw` чипы
(`wildcard`, `freehit`, `bboost`, `3xc`), а не только Wildcard; правило WC не изменилось.

### Режимы

- **`best_xi(squad, gw, strategy)`** — `W = {gw}`, `max_transfers = 0`: 87 переменных, 0.01 с.
  Скамейка: вратарь в слоте 12, полевые по убыванию xPts.
- **`single_transfer(squad, bank, ft, pool, gw, horizon=3, strategy, exclude, keep, allow_hit)`**
  — трансферы только в `gw`, лимит 1 (2 при FT ≥ 2), `+1` платный при `allow_hit`; лучшие 11
  оптимизируются в каждом туре горизонта (value состава на будущие туры = его лучшие 11 + капитан,
  а не сумма 15). Top-3 через **канонические no-good cuts** по набору покупок:
  `Σ_{p∈S} t_in − Σ_{p∉S} t_in ≤ |S| − 1` — запрещает ровно набор `S`, надмножества остаются
  (первая версия `Σ_S ≤ |S|−1` для одиночного `S` запрещала игрока целиком). Смена продаваемого
  энейблера при тех же покупках новым маршрутом не считается.
  Метрики маршрута против «без трансферов»: `Δnext` (следующий тур), `Δhor` (сумма по горизонту),
  `Δdisc` (с дисконтом), `Δobj` (разность целей: учитывает ft_value, скамейку, λ, ω).
  **Вердикт по хиту** считается от лучшей *бесплатной* альтернативы (отдельный solve), а не от
  «ничего не делать»: `hit_marginal_gain = Δdisc(маршрут) − Δdisc(лучший бесплатный) − 4`,
  `go` если `≥ hit_threshold` и цель выше; иначе `hit_not_worth`. Бесплатный маршрут — `hold`,
  если `Δobj ≤ 0` (апгрейд не окупает потерю FT). `recommend_route` = первый `go`.
- **`plan_transfers(squad, bank, ft, chips, from_gw, horizon=5, strategy, pool, issues)`** —
  трансферы в каждом туре (≤ 4 за тур), FT копятся до 5; baseline — тот же solve с
  `max_transfers = 0` (лучшие 11 каждого тура без трансферов, FT копятся). Если Wildcard доступен
  — второй solve с WC в `from_gw`; далее обычные трансферы. Рекомендация:
  `wildcard`, если `WC.expected_total − plan.expected_total > wc_margin` **и** проблемных
  игроков (severity ≥ 2 в `diagnose_squad`) ≥ 3; `hold`, если в `from_gw` ноль трансферов; иначе
  `transfers`. `expected_total = Σ_w (XI + капитан + вклад фишки − 4·paid[w])` без дисконта — то,
  что видит пользователь; `objective` — значение цели модели. `chips={gw: "bboost"|"3xc"}` —
  фишки в турах (раздел выше); входят в план, baseline и WC-альтернативу.

Пары out→in внутри тура собираются по позиции (квоты состава фиксированы ⇒ по позиции
`#in = #out`), внутри позиции — по убыванию цены; `delta_xpts_horizon` — xPts(in) − xPts(out) с
тура хода до конца горизонта; `out_problem` — вид проблемы из `diagnose_squad`; `paid` — ход
платный (последние по Δ пары в туре).

## Стратегии (`core/strategy.py`)

Стратегия — только коэффициенты цели и порогов; текст она не меняет.

| параметр | conservative | balanced | aggressive | смысл |
|---|---|---|---|---|
| `variance_penalty` λ | 0.03 | 0.01 | −0.005 | очков штрафа за 1 очко² дисперсии стартера за тур (дисперсия стартеров v0: квартили 4.5 / 5.9 / 7.8, Haaland ≈ 17); отрицательное = премия за дисперсию (погоня за рангом) |
| `hit_threshold` | 2.0 | 1.0 | 0.25 | минимальный `hit_marginal_gain`, чтобы советовать −4 |
| `ownership_weight` ω | +0.005 | 0 | −0.005 | очков за 1 % владения на игрока состава за тур: 70 %-й игрок ≈ ±0.35/тур |
| `wc_margin` | 3.0 | 2.0 | 1.0 | на сколько очков WC должен обыграть план трансферов |
| `ft_value` | 1.5 | 1.5 | 1.5 | ценность FT (community default) |
| `itb_value` | 0.08 | 0.08 | 0.08 | очков за £1 млн в банке за тур (community default) |
| `decay_base` | 0.84 | 0.84 | 0.84 | дисконт будущих туров (community default) |
| `bench_weights` | {12: 0.03, 13: 0.21, 14: 0.06, 15: 0.002} | | | доля xPts запасного по слоту (community default) |

Источник дефолтов: sertalpbilal/FPL-Optimization-Tools, `dev/solver.py` (`decay_base 0.84`,
`bench_weights {0: 0.03, 1: 0.21, 2: 0.06, 3: 0.002}`, `ft_value 1.5`, `itb_value 0.08`). λ, ω,
пороги — наши: подобраны так, чтобы менять решения на границе (0.3–0.5 очка/тур), а не
переворачивать состав. На реальном составе GW5 balanced и aggressive дали одинаковый план —
разрывы в xPts больше этих поправок; расходятся они на маршрутах с хитом (см. ниже).

## Пул кандидатов (`candidates.build_pool`)

Текущий состав целиком (в т.ч. травмированные — их надо уметь продать) + top-`size` (120) по
сумме xPts за горизонт с квотами по позициям 2/5/5/3 от 15 (GKP 16, DEF 40, MID 40, FWD 24) +
по 6 лучших дешёвых на позицию (GKP/DEF ≤ £4.5, MID ≤ £5.0, FWD ≤ £5.5 — энейблеры, которых в
топе нет, но без них не собрать бюджет). Вне пула: статусы `i/s/u/n` (кроме состава), `--exclude`,
цена выше `bank + самый дорогой игрок состава`, нулевой xPts за горизонт. На GW5: 159 игроков.

## Диагностика состава (`candidates.diagnose_squad`)

| kind | правило | severity |
|---|---|---|
| injured / suspended / unavailable | статус FPL `i / s / u,n`, либо сигнал новостей `injured/suspended/unavailable` при статусе `a` | 3 |
| doubtful | статус `d`: chance ≤ 50 → 2, иначе 1 | 1–2 |
| not_playing | `p_start < 0.5` или `exp_minutes < 45` (запасной вратарь исключён) | 2 |
| low_xpts | только для лучших 11: xPts за горизонт ниже медианы позиции среди регулярных стартеров (`p_start ≥ 0.6`) | 2 |
| fixtures | средний индекс силы фикстур за горизонт ≥ 4.0 | 1 |
| blank | нет матча в `from_gw` | 1 |

`problem_players` = игроки с severity ≥ 2 — вход правила Wildcard.

## Допущения, которые владельцу стоит проверить

1. **Цена продажи = текущая цена.** Публичный API не отдаёт `selling_price` (нужна авторизация);
   реальная продажа даёт половину роста цены с момента покупки. Для менеджеров с большим ростом
   стоимости команды бюджет модели завышен на десятые миллиона. Цены на горизонте статичны.
2. **Оценка FT** — по истории трансферов (`estimate_free_transfers`), API её не отдаёт.
3. **Состав = picks последнего завершённого тура.** До дедлайна публичный API не показывает уже
   сделанные трансферы текущего тура.
4. **Wildcard доступен/сыгран** — по именам чипов из истории; `--wc/--no-wc` перебивают. Так же
   (по именам и окнам `bootstrap.chips`) считаются Bench Boost / Triple Captain: в первой
   половине чип доступен, если такой не сыгран, во второй — если сыграно меньше двух.
5. **Константы стратегий** (λ, ω, пороги, `wc_margin`, «≥ 3 проблемных») — экспертные, не
   калиброванные; community-дефолты (`ft_value`, `itb_value`, `decay`, `bench_weights`) — как есть.
6. **Дисперсия v0** — эвристика (docs/xpts.md), поэтому λ мал; правило хита использует чистые
   xPts, а не цель с λ/ω.
7. **WC-состав без Haaland** (пример ниже) — следствие v0: при £15.5 его 7.1 xPts проигрывают по
   очкам на миллион; это про модель xPts (премиумы, бонус FWD), а не про оптимизатор.

## Ограничения

- Чипы: Wildcard — сравнение в первом туре горизонта; Bench Boost и Triple Captain — только как
  заданное пользователем условие «фишка → тур» (солвер не выбирает, *когда* играть фишку).
  **Free Hit не моделируется** (состав на один тур с возвратом — отдельная ветка модели).
- Чат пока не извлекает фишку из фразы («в GW7 играю BB»): роутер/граф агента не трогались,
  `build_gameweek_plan(chips=…)` из агента не вызывается; фишку задают CLI (`--chip`) и страница
  «План». MCP-инструмент `build_gameweek_plan` тоже без параметра фишек.
- Страница «План» предлагает фишки, доступные на `from_gw`; если горизонт переходит через GW19→20
  и чип первой половины уже сыгран, второй набор в списке не появится (сервер его примет — это
  ограничение только выбора в UI).
- TC не меняет штраф дисперсии капитана (как и удвоение капитана без фишки — риск считается по
  стартерам с весом 1).
- Цены статичны; автозамены и «капитан не сыграл → вице» не моделируются (вице — лучший стартер).
- Blank/double GW обрабатываются через `xpts_by_gw` (0 при blank, сумма матчей при double).
- Цель — линейная в матожиданиях; корреляции (сухарь двух защитников одного клуба) не учитываются.
- Многотуровый план — «жёсткий»: он оптимизирует ожидания на 5 туров, а реальный совет — только
  ближайший ход; остальное — направление, которое пересчитывается каждый тур (`diff_plans`).

## Снимки планов (`core/plan.py`, `006_plans.sql`)

`plan_snapshots(id, manager_id, gw, strategy, horizon, plan jsonb, inputs_hash, created_at)`.
`inputs_hash` — sha1 от состава, банка, FT, стратегии, горизонта и xPts пула (округлены до 0.01):
совпал — план можно не пересчитывать. `diff_plans(prev, new)` — структурный diff ходов:
`added / removed / changed_target` (тот же out, другой in) / `moved_gw` (та же пара в другом туре)
+ `recommendation`. Причины diff («Palmer получил травму») выводит агент, глядя на `issues`.
