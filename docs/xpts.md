# xPts v0: компонентная модель ожидаемых очков

Пакет `src/fplcopilot/core/` — детерминированное ядро: LLM здесь не вызываются никогда.
Цель — по данным FPL API (история матчей, статусы, фикстуры) и сигналам из новостей
(`player_signals`, `docs/rag.md`) получить для каждого игрока ожидаемые очки на тур **с разбивкой по
компонентам правил FPL**, чтобы агент объяснял «почему», а не «сколько».

```
element-summary ──sync──▶ player_gw_history / player_season_history ─┐
bootstrap (статусы, ep_next), fixtures ─────────────────────────────┤
player_signals (rag/extract, as_of <= дедлайн) ─────────────────────┤
                                                                     ▼
   core/history.rows_before (leakage guard) ─▶ core/minutes (p_start, exp_minutes, p60)
   core/fixtures.TeamRatingProvider (xg_for / xg_against по матчу) ◀─ fallback ─ core/odds.OddsProvider
   The Odds API h2h (кэш .cache/odds, TTL 6 ч) ─▶ медиана 1/X/2 ─▶ снятие маржи ─▶ Пуассон ─▶ λ ──┘
   core/xpts: ставки per-90 со сжатием ─▶ компоненты ─▶ XPtsBreakdown ─▶ xpts_predictions
   core/backtest (walk-forward GW2–4), scripts/gw_review.py (разбор тура после свистка)
```

```bash
uv run python -m fplcopilot.core.history --sync [--refresh]         # element-summary всех игроков -> БД
uv run python -m fplcopilot.core.xpts --gw 5 --top 25 [--position MID] [--save]
uv run python -m fplcopilot.core.xpts --gw 6 --top 15 --provider odds [--model-version v0-odds --save]
uv run python -m fplcopilot.core.xpts --player Haaland --horizon 3
uv run python -m fplcopilot.core.xpts --explain "João Pedro"
uv run python -m fplcopilot.core.backtest --gws 2,3,4               # -> docs/xpts_backtest.json
uv run python scripts/gw_review.py --gw 5 --sync                    # после завершения тура
```

## Данные (миграция `005_core.sql`, `core/history.py`)

| таблица | что | ключ |
|---|---|---|
| `player_gw_history` | строка игрока за матч (зеркало `PlayerGWHistory`: минуты, старты, очки, xG/xA/xGC, saves, BPS, CBI/tackles/recoveries, карточки) | `(season, player_id, fixture)` |
| `player_season_history` | итоги прошлых сезонов из `history_past` — приор для per-90 ставок и p_start | `(player_id, season_name)` |
| `xpts_predictions` | прогноз: `xpts, p_start, exp_minutes, components (jsonb), variance, ep_next_snapshot` | `(player_id, gw, model_version, as_of)` |

`sync_history` идемпотентен (upsert; бонусы/BPS уточняются после тура), тянет element-summary
всех игроков через дисковый кэш `FPLClient` с паузой 0.07 с после каждого сетевого запроса.
Прогон на данных GW1–4: **659 игроков, 2549 строк GW1–4, 2097 строк прошлых сезонов, 656 сетевых
запросов, 135 с**. Командные xG за/против по матчу не хранятся — `team_match_stats(gw_max)`
считает их на лету как сумму `expected_goals` игроков каждой стороны.

Проверено на данных: поле `defensive_contribution` в API — это **счётчик** CBIT (DEF) / CBIRT
(MID/FWD), а не очки; совпадает с нашим `scoring.defcon_count` на всех 2549 строках.

## Правило без исключений: утечка из будущего

Прогноз на тур `g` строится по контексту `make_context(g, as_of)`:

- история — `rows_before(rows, g, as_of)`: только `round < g` **и** `kickoff_time < as_of`
  (второе условие — против перенесённых матчей ранних туров, сыгранных после дедлайна);
- `as_of = min(запрошенное время, дедлайн g)` — нельзя «знать» больше, чем на дедлайн;
- сигналы новостей — последний на игрока с `as_of <= дедлайн` и не старше 7 дней
  (`core/signals.latest_signals`);
- статусы FPL: если `as_of` — «сейчас» (±10 мин), берётся живой bootstrap; снимков статусов на
  дедлайны GW1–4 нет (`player_status_snapshots` пишутся начиная с GW5), поэтому бэктест считает всех доступными, кроме
  игроков без единой минуты во всех предыдущих раундах (`status_overrides` -> `u`);
- приоры позиции считаются по тому же окну (`position_priors`), а не по всему сезону.

Покрыто тестами: фильтр по раунду и по кикоффу, строка раунда 2 с xG=5 не попадает в контекст GW2.

## Модель минут (`core/minutes.py`)

1. `p_start_raw = 0.7 · взвешенная доля стартов в последних 5 матчах (веса 0.35/0.25/0.18/0.12/0.10)
   + 0.3 · доля стартов за сезон`;
2. сжатие к приору: `p_start = (n · p_start_raw + 1 · prior) / (n + 1)`, `prior` — доля стартов
   прошлого сезона (`starts / 38`), без прошлого сезона — 0.4. Четыре старта из четырёх дают
   ~0.9–0.95, а не 1.0;
3. `p_sub = P(выход на замену | не старт)` (приор 0.35), минуты замены (приор 20), минуты при
   старте (приор GKP 90 / DEF 86 / MID 80 / FWD 78) и `P(>=60 | старт)` (0.99/0.95/0.88/0.85) —
   по тем же строкам со сжатием `k = 2`;
4. доступность FPL — множитель к `p_start` и `p_sub`: `a` -> 1 (или `chance/100`, если FPL его
   указал), `d` -> `chance/100` (нет chance -> 0.5), `i/s/u/n` -> 0;
5. сигнал новостей (не `unknown`, `confidence > 0`): `p_start = w · signal.start_probability +
   (1 - w) · p_start`, `w = confidence`; `injured/suspended/unavailable` гасят и `p_sub` на `(1 - w)`.
   **Исключение `fit`:** снизить `p_start` он может только с `rotation_risk = high` (явное
   предупреждение о ротации); типовой «fit 0.9» лишь подтверждает прогноз (Haaland: 0.98 остаётся
   0.98; при обычном смешивании сигнал резал его до 0.92) или поднимает игрока со статусом `d`;
6. горизонт (`gw > status_gw`, где `status_gw` — тур, к которому относится статус FPL): если у
   сигнала есть `return_gw`, то для `gw < return_gw` доступность `= 0` (для статуса `d` —
   `chance/100`), для `gw >= return_gw` статус и сигнал игнорируются, первый тур после
   возвращения получает `×0.8` (`POST_RETURN_DISCOUNT`: ввод через замену / ранняя замена).
   Без `return_gw` статус ближайшего тура переносится на весь горизонт.

Выход: `exp_minutes`, `p_appear = p_start + (1 - p_start) · p_sub`,
`p60 = p_start · p60_start + (1 - p_start) · p_sub · 0.04`. Всё, что вошло в решение, попадает в
`notes` и печатается `--explain`.

## Ставки per-90 и сжатие (`core/xpts.py`)

Для каждого игрока считаются xG, xA, saves, BPS, CBIT, CBIRT, жёлтые — на 90 минут.

- **Приор игрока** = прошлый сезон 2025/26 (`player_season_history`) с весом `m / (m + 900)`,
  остальное — приор позиции. Прошлый сезон есть у 476 игроков (409 с минутами); у новичков лиги —
  только приор позиции.
- **Приор позиции** — средние per-90 по всем строкам окна (эмпирический Байес); при < 900 минут в
  окне берутся константы `FALLBACK_PRIORS`. На GW1–4 2026/27:

| позиция | xG90 | xA90 | saves90 | BPS90 | CBIT90 | CBIRT90 | YC90 |
|---|---|---|---|---|---|---|---|
| GKP | 0.000 | 0.004 | 2.90 | 15.7 | 1.35 | 10.2 | 0.025 |
| DEF | 0.067 | 0.059 | — | 13.4 | 7.52 | 10.97 | 0.177 |
| MID | 0.165 | 0.127 | — | 20.4 | 3.90 | 8.14 | 0.201 |
| FWD | 0.446 | 0.062 | — | 19.5 | 1.73 | 4.10 | 0.193 |

- **Сжатие сезона к приору** в единицах минут: `rate90 = (сумма + prior · 450/90) / (minutes + 450) · 90`
  — после 4 полных матчей данные сезона весят 44 %, приор 56 %. Это осознанно тяжёлое сжатие:
  четыре матча — шум (см. DefCon-бакеты ниже).

## Сила фикстур (`core/fixtures.py`, `core/odds.py`)

Протокол `FixtureStrengthProvider.expected_goals(fixture) -> (home_xg, away_xg)`; из него для
каждой команды строится `FixtureView(xg_for, xg_against, clean_sheet_prob = exp(-xg_against),
fixture_strength_index 1–5, fsi_source = 'odds' | 'team_rating')`. Выбор реализации —
`XPTS_FIXTURE_PROVIDER=team_rating|odds` (дефолт — `team_rating`; `odds` включается
`XPTS_FIXTURE_PROVIDER=odds`, так настроен `.env.prod.example`).

**`TeamRatingProvider` (по умолчанию).** `λ_home = L · att_h · def_a · 1.10`,
`λ_away = L · att_a · def_h · 0.90`, `L = 1.45` (среднее xG команды за матч в АПЛ; факт GW1–4 —
1.51 xG и 1.43 гола). Множители `att/def` — сжатие данных сезона (xG за / против на матч
относительно среднего по лиге) к рейтингу FPL с весом `n / (n + 6)`: после 4 туров данные весят
40 %. Рейтинг FPL: в 2026/27 API отдаёт `strength_attack_* = strength_defence_* = 0`, поэтому
используется `strength_overall_home/away` (2–5): `att = (s / s̄)^0.75`, `def = (s̄ / s)^0.75`.
Показатель 0.75 выбран так, чтобы ARS(д) – COV давало ≈ 2.8–0.7 xG (уровень букмекеров); по 40
матчам GW1–4 MAE рейтингов к факту почти не зависит от показателя (0.5 -> 0.67, 0.75 -> 0.69,
1.0 -> 0.73), корреляция 0.29 — рейтинги FPL грубые, потому данные сезона и нужны. После сборки
все λ масштабируются так, чтобы среднее по 380 матчам сезона было ровно `L`.

`fixture_strength_index` по разности `xg_for − xg_against`: ≥ +0.9 -> 1 (очень лёгкая), ≥ +0.3 -> 2,
≥ −0.3 -> 3, ≥ −0.9 -> 4, иначе 5. Это единственное, что видит пользователь, — источник
(рейтинги или коэффициенты) внутренний. GW5 (`team_rating`, данные до дедлайна GW5):

**`OddsProvider` (`core/odds.py`, The Odds API v4).** `GET /v4/sports/soccer_epl/odds?regions=eu&
markets=h2h&oddsFormat=decimal` через httpx (таймаут 10 с) -> дисковый кэш
`.cache/odds/epl_h2h.json` с TTL `ODDS_CACHE_TTL` (6 ч; бесплатный тариф — 500 запросов/месяц,
заголовки `x-requests-used/remaining` пишутся в лог, при 4 обновлениях в сутки уходит ≈ 120/мес)
-> по матчу **медиана** десятичных коэффициентов 1/X/2 по всем букмекерам (22 в снимке GW6–7;
устойчива к одиночным кривым линиям) -> `remove_margin` (пропорциональное снятие маржи) ->
`xg_from_1x2_and_total(..., None, None)` (подбор `λ_home, λ_away` по сетке Пуассона под 1X2,
шаг 0.02, затем 0.002) -> те же `xg_for / xg_against`, что у рейтингов.

- *Сопоставление с FPL:* имена команд API («Manchester United», «Brighton and Hove Albion»,
  «Nottingham Forest», «Tottenham Hotspur», …) -> нормализация (регистр, диакритика, апострофы,
  `&`, `FC`) + явный словарь алиасов (`TEAM_ALIASES`, 40 клубов АПЛ/Чемпионшипа) -> `teams[].name`
  или `short_name`; матч привязывается к фикстуре по паре (хозяева, гости) и ближайшему
  `kickoff_time` (допуск 72 ч). Живой снимок GW6–7: **20/20 матчей сопоставлены** с фикстурами
  GW6 (10) и GW7 (10), расхождение `commence_time` и `kickoff_time` — 0 у всех. Несопоставленный
  матч -> warning и `team_rating` для этой пары.
- *Гибрид:* рынок покрывает 1–2 ближайших тура, поэтому для остальных фикстур (при снимке GW6–7 —
  GW8+) провайдер прозрачно отдаёт `TeamRatingProvider`; `fsi_source` в `FixtureView` / `FixtureInput` /
  `FixtureBrief` говорит UI, чем посчитана сложность («по букмекерам» / «по рейтингу команд»).
  Без `ODDS_API_KEY`, без сети и без кэша — один warning и целиком `team_rating`; при ошибке сети
  с протухшим кэшем — кэш с предупреждением о возрасте. Исключений наружу нет.
- *Уровень голов:* по одному рынку 1X2 тотал идентифицируется плохо — Пуассон занижает долю
  ничьих, и подгонка под рыночную P(X) даёт в среднем 1.28 xG на команду (тотал 2.56 против ≈ 2.9
  в АПЛ). Поэтому, как и у рейтингов, все λ снимка масштабируются к `L = 1.45` (снимок GW6–7: ×1.096);
  относительные силы и доля хозяев остаются рыночными. С рынком totals (`markets=h2h,totals`,
  ×2 запросов) масштаб не нужен — кандидат на v1.
- *Guardrail:* коэффициенты и вероятности исходов — только внутри `MatchOdds`; в `FixtureView`,
  `FixtureInput`, `FixtureBrief`, JSON `--json` и заметках модели их нет (тест
  `test_prediction_json_has_source_label_but_no_odds`). Ключ не попадает в логи httpx и тексты
  ошибок.

## Компоненты (`fixture_components`)

Для игрока позиции `pos`, матча `f`, `m = exp_minutes / 90`; фактор атаки
`att_f = xg_for(f) / базовый xg_for команды`, фактор обороны `def_f = xg_against(f) / базовый
xg_against` (базовый — среднее по всем 38 матчам сезона глазами провайдера). Деление на **базу
команды**, а не на среднее лиги, — чтобы не удваивать силу клуба: xG90 игрока уже содержит атаку
его команды.

| компонент | формула | заметки |
|---|---|---|
| appearance | `p_appear · 1 + p60 · 1` | |
| goals | `(xG90 + 0.05·[penalties_order = 1]) · m · att_f · pts_goal[pos]` | 10/6/5/4 |
| assists | `xA90 · 1.35 · m · att_f · 3` | ассисты FPL шире Opta xA: GW1–4 — 26 ассистов за тур при 18.2 суммарного xA (×1.43); берём 1.35 |
| clean_sheet | `p60 · exp(−xg_against) · pts_cs[pos]` | 4/4/1/0 |
| goals_conceded | `−p60 · E[floor(Poisson(xg_against) / 2)]` | GKP/DEF; точное матожидание вместо `0.5·λ` (0.49 против 0.73 при λ = 1.45) |
| saves | `E[floor(Poisson(saves90 · m · def_f) / 3)]` | GKP; наивное `λ/3` завышало сумму на 50 % |
| defcon | `2 · [p_start · P(N(rate90·min_start/90) ≥ T) + (1−p_start) · p_sub · P(N(rate90·min_sub/90) ≥ T)]` | `T` = 10 CBIT (DEF) / 12 CBIRT (MID, FWD); `N` — отрицательный биномиал с `Var = 1.3 · mean` |
| bonus | `BONUS_MAX[pos] · pct(BPS90 внутри позиции)^3 · m` | `BONUS_MAX` = GKP 0.9 / DEF 0.85 / MID 1.2 / FWD 1.5; перцентиль среди игроков позиции с минутами в окне |
| cards | `−yellow90 · m` | красные не моделируются |
| setpiece | `XPTS_SETPIECE_WEIGHT · [penalties_order=1] · min(1, m)` + `XPTS_FREEKICK_WEIGHT · [dfk_order=1] · min(1, m)` | аддитивный слой, не переписывает формулу голов; дефолт 0.12 / 0.03; blank / 0 минут = 0 |

### Внешняя стата: FPL-стандарты + Understat (`core/understat.py`, `core/ext_stats.py`)

Основной сигнал — таблица выше. Understat и очередь стандартов FPL дают **маленький аддитивный сдвиг**; каждый регулируется одним числом в конфиге:

| константа | дефолт | что делает |
|---|---|---|
| `XPTS_SETPIECE_WEIGHT` | 0.12 | +xPts за тур первому пенальтисту (`penalties_order = 1`), × `min(1, exp_minutes/90)` |
| `XPTS_FREEKICK_WEIGHT` | 0.03 | то же для `direct_freekicks_order = 1` |
| `XPTS_UNDERSTAT_BLEND` | 0.25 | `0.75 · наш xG90/xA90 + 0.25 · Understat`; сдвиг per-90 не больше ±`XPTS_UNDERSTAT_SHIFT_CAP` (0.15) |
| `XPTS_SAVES_WEIGHT` | 0 | сейвы GKP уже в компоненте `saves`; вес 0, чтобы не двоить |

Поля `setpiece_bonus` и `understat_blend` пишутся в `FixtureInput`, `XPtsBreakdown` и заметки модели. Живые прогнозы помечаются `model_version = v0-ext`; снимок эксперимента GW5/GW6 (`v0`) не перезаписывается.

Источник: FPL bootstrap (пенальтист / штатник / сейвы / xG) + публичный JSON Understat `GET /getLeagueData/EPL/2026` (страница лиги не кладёт `playersData` в HTML; парсер HTML-варианта с `JSON.parse` сохранён для тестов и fallback). Кэш `.cache/understat/`, TTL 12 ч. Нет сети / пустой сезон — только FPL, приложение не падает.

**Не используются:** фолы команды и стандарты соперника. Understat их стабильно не отдаёт; FBref не скрапим (вёрстка, нет публичного JSON). Кандидат на следующий источник. Командный xGA Understat используем как «мало пропускает» (MCP `get_team_defensive_profile`).

Почему отрицательный биномиал для DefCon: pooled `Var/mean` счётчика по матчам ≥ 60 минут GW1–4
= 1.28 (DEF 1.48, MID 1.14); leave-one-out по бакетам среднего показал, что Пуассон занижает
шанс у игроков ниже порога и завышает у игроков выше (частично это регрессия к среднему, которую
лечит сжатие, частично — сверхдисперсия).

`xpts = сумма компонентов` (тест: сумма равна итогу для каждого игрока); blank GW -> все нули,
double GW -> сумма по матчам с той же моделью минут. **Дисперсия** — эвристика: биномиальные
члены для вероятностей (появление, p60, сухарь, DefCon), пуассоновские для счётчиков (голы ×
pts², ассисты × 9, сейвы, карточки), бонус ≈ своему матожиданию.

## Ограничения v0

- 4 тура данных: всё держится на сжатии; приоры позиции и константы калибровки выведены из тех
  же GW1–4.
- Статусы на прошлые дедлайны отсутствуют — бэктест переоценивает травмированных; горизонт > 1
  тура использует текущий статус, если у сигнала нет `return_gw` (с `return_gw` — см. п. 6 модели
  минут; `×0.8` в первый тур после возвращения — экспертная константа, не калибровалась).
- Не моделируются: автоголы, незабитые/отбитые пенальти, красные карточки, DefCon-зависимость от
  соперника (у слабых команд больше оборонительных действий), корреляция сухаря и минут.
- Пуассон занижает сухари; бонус FWD недобирается; рейтинги FPL 2026/27 без атаки/защиты.
- `history_past` покрывает только игроков, бывших в FPL; новички лиги стартуют с приора позиции.
- Коэффициенты покрывают только 1–2 ближайших тура (гибрид с рейтингами дальше по горизонту), один
  рынок 1X2 без totals (уровень голов масштабируется к L), снимок обновляется раз в 6 ч, а не
  «за N часов до дедлайна»; без Диксона–Коулза ничьи в подгонке λ занижены.

## Идеи для v1

- LightGBM/линейная модель на исторических данных (vaastav FPL, 2016–2026) для per-90 ставок и
  минут; текущие компоненты — фичи и объясняющий слой поверх.
- `OddsProvider`: рынок totals (уровень голов из рынка вместо масштаба к L) + Диксон–Коулз,
  снимок за фиксированное время до дедлайна; DefCon как NegBin с фактором соперника.
- Бонус через ожидаемые возвраты (голы/ассисты/сухарь) вместо перцентиля BPS.
- Честный бэктест доступности по снимкам статусов на каждый дедлайн (`player_status_snapshots`
  пишутся начиная с GW5).
- Калибровка дисперсии по фактическим остаткам после 6–8 туров.
